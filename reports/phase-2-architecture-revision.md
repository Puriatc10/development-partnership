## 1. Executive Summary & Purpose

Following two rigorous audit iterations of the Phase 2.1 architecture, this report documents the consolidated findings, structural issues discovered, exact database corrections implemented, and the final hardened implementation.

All work preserves the foundational reality: **the planned technical delivery team is not yet onboarded and not currently available for client delivery**.

---

## 2. Issues Discovered in Earlier Iterations

Our audit identified eight structural, security, compliance, and referential vulnerabilities:

1. **Negative-Matching Agent Security Flaw:** The earlier draft used `NOT is_human_operator()` in agent RLS policies. This inadvertently granted agent access to unknown, client, or unverified authenticated roles.
2. **Silent Admin Identity-Mismatch Bypass:** Outreach approval previously allowed admins to approve under any arbitrary `approved_by_human_id` without an audit trail, bypassing strict personal attribution.
3. **Cross-Entity Referential Inconsistency:** Child records (e.g. `outreach_messages.contact_id` and `company_id`) were independently checked, allowing data corruption where an outreach message or activity could reference a contact belonging to a completely different company.
4. **Suppression Incomplete on Channel Changes:** If an opted-out contact changed their email or had a LinkedIn profile, historical updates did not reliably populate `suppression_registry`. Deletions of suppression records were not explicitly blocked at the schema level.
5. **Subjective Lead Scoring & Tier Assignment:** The earlier schema allowed positive dimension scores without requiring verified evidence, and allowed arbitrary qualification tier assignments that conflicted with the 100-point rubric.
6. **Caller-Supplied Approval Timestamps & Mutation Tampering:** Approval timestamps were accepted from caller parameters rather than generated by trusted database logic, and approved messages could be materially altered after approval without invalidating the approval status.
7. **Timezone Distortion in Working-Day Calculation:** The `add_business_days` function was incorrectly declared `IMMUTABLE` and did not evaluate day-of-week boundaries in the partner's operating timezone.
8. **Premature Migration Complexity:** All 18 tables were bundled into a single initial migration despite four delivery tables belonging strictly to a post-agreement execution phase.

## 3. Exact Changes Made in Final Hardening

| Area | Prior Implementation | Final Hardened Implementation |
| :--- | :--- | :--- |
| **Migration Structure** | Single 18-table monolithic migration | **Separated into two migration files:** `crm/schema.sql` (14 MVP Core tables) and `crm/phase2_delivery_expansion.sql` (4 Delivery tables). |
| **Agent Authentication & RLS** | Negative matching: `NOT is_human_operator()` | **Explicit positive matching:** `is_agent()`, `is_agent_type()`, and `current_agent_identity()`. Unknown roles receive zero access. |
| **Subagent Privilege Isolation** | Blanket agent access across tables | **Least privilege per subagent type:** Researchers write reports; Qualifiers write draft scorecards; Drafters write draft outreach. |
| **Task Queue Security** | Agents could view/update any task | **Row-level task ownership:** Agents can only view and update tasks assigned to their verified `current_agent_identity()`. |
| **Cross-Entity Integrity** | Independent foreign keys | **Composite Foreign Keys:** `(contact_id, company_id)` on `outreach_messages` and `activities`; `(report_id, company_id)` on `research_findings`; `(partnership_id, company_id)` on `projects`. |
| **Suppression Synchronization** | Partial email-only sync | **Multi-channel sync:** Emails, domains, LinkedIn handles, and phone numbers. Deletions from `suppression_registry` are blocked by trigger. |
| **Pre-Dispatch Suppression Gate** | Unverified dispatch risk | **Mandatory pre-dispatch check:** Verifies email, domain, and LinkedIn handle before transition to `queued`, `sending`, or `sent`. |
| **Human Approval Attribution** | Caller-supplied `approved_at`; admin mismatch bypass | **Strict `auth.uid()` matching:** Overwritten with `clock_timestamp()`. Administrative overrides require explicit audit flags (`is_admin_override`, `override_reason`). |
| **Approval Invalidation** | Approved content could be modified without check | **Automatic Invalidation:** Modifying approved outreach content or approved scorecard scores automatically resets status to `draft`. |
| **Evidence-Based Qualification** | Unverified JSONB structure | **Database trigger validation:** Any dimension score $> 0$ requires documented evidence in `dimension_evidence`. Tiers are deterministically enforced. |
| **Audit Log Integrity** | Unprotected audit ledger | **Trusted `SECURITY DEFINER` capture trigger** + trigger blocking all manual `UPDATE` and `DELETE` on `audit_logs`. |
| **Business-Day Calculation** | `IMMUTABLE` calendar function | **`STABLE` timezone-aware function** evaluating partner local time zone (`companies.timezone`). |
| **Domain Deduplication** | Disconnected primary domain and domain aliases | **Automatic sync trigger:** Upserts `primary_domain` into `company_domains` automatically. |

## 5. Revised Security and RLS Architecture

### 5.1. Enforcement Hierarchy
1. **Network / Anonymous:** Deny-all on 100% of tables for `anon`.
2. **Role Claim Verification:** Functions `is_human_operator()` and `is_agent()` inspect `auth.jwt() -> 'app_metadata'`.
3. **Subagent Scoping:** Researcher, Qualifier, and Drafter agents can only write to their designated draft tables.
4. **Trigger Defense-in-Depth:** Procedural triggers verify that calling users are human operators, match `auth.uid()`, and check suppression immediately before dispatch.
5. **Service-Role Isolation:** The Supabase `service_role` key is strictly withheld from Hermes agents, client code, and public repositories.

## 6. Restored Seven-Dimension Lead Scoring Model

The qualification model restores the approved seven dimensions (100 points maximum):

$$\text{Overall Score} = \text{Customer Flow (20)} + \text{Dev Demand (20)} + \text{Repeatability (15)} + \text{Technical Fit (15)} + \text{Size (10)} + \text{DM Access (10)} + \text{Commercial Fit (10)}$$

### Dimension Column Mappings & Constraints
1. `customer_flow_score`: Evidence of customer flow (0–20 pts)
2. `development_demand_score`: Evidence of development demand (0–20 pts)
3. `repeatability_orders_score`: Repeatability of orders (0–15 pts)
4. `technical_fit_score`: Technical fit (0–15 pts)
5. `business_size_score`: Business size (0–10 pts)
6. `decision_maker_accessibility_score`: Decision-maker accessibility (0–10 pts)
7. `commercial_fit_score`: Commercial fit (0–10 pts)

### Logical Review of Qualification Tiers
- **Tier 1 Priority (80–100 Points):** Strong performance across primary operational drivers with high technical and commercial alignment. Fast-tracked for personalized outreach.
- **Tier 2 Prospective (60–79 Points):** Solid potential fit, verifiable recurring demand, but minor information gaps regarding contract repeatability or exact team size. Proceed with discovery.
- **Tier 3 Deferred (40–59 Points):** Niche studio or expansion segment (e.g. e-commerce agency) requiring later review.
- **Disqualified (< 40 Points or Disqualification Trigger):** Speculative entities with no clients, commodity price shoppers, or entities lacking project scoping maturity.

## 7. Suppression and Deletion Guarantees

1. **Independent Ledger (`suppression_registry`):** Decoupled from core entities without foreign key constraints. Deleting a contact or company record does not delete their suppression entries.
2. **Multi-Channel Coverage:** Email, domain, LinkedIn handle, and phone numbers are normalized and stored permanently.
3. **Automatic Synchronization:** Opt-outs and channel updates on opted-out records automatically populate `suppression_registry`.
4. **Pre-Dispatch Verification:** Trigger `fn_enforce_outreach_human_approval` verifies email, domain, and LinkedIn handle before dispatch.
5. **Deletion Immutability:** Trigger `fn_enforce_suppression_immutability` blocks any `DELETE` on `suppression_registry`.
6. **Commercial History Protection:** `ON DELETE RESTRICT` is enforced on companies and contacts that have existing outreach messages, conversations, or partnerships.

## 8. Revenue and Retainer Coverage Boundaries

### 8.1. Separation of Financial Concepts
1. **Project Commercial Value:** Contracted SOW value, stored in `projects.commercial_value`.
2. **Expected Revenue:** Pipeline probability weighting calculated in CRM queries based on conversation stage.
3. **Invoiced Amount:** Formally deferred to the Delivery & Finance phase (`invoices` table).
4. **Collected Payments:** Upfront milestone kickoff deposits tracked in `projects.deposit_paid` and `deposit_paid_at`; full cash reconciliation deferred.
5. **Direct Project Costs:** Formally deferred to Delivery & Finance (contractor expenses, compute).
6. **Gross Profit:** Formally deferred to Delivery & Finance (`collected - direct_costs`).
7. **Monthly Reserved Capacity:** Modeled as a strategic commercial enum value (`monthly_reserved_capacity`), but capacity allocation tables, hourly burn logs, and rollover mechanics are formally deferred to Phase 3.

1. **Supabase Region Selection (D-01):** Unresolved. Must be selected based on primary target partner geography and GDPR compliance posture (e.g. Frankfurt vs. N. Virginia).
2. **Currency Model (D-02):** Unresolved. Stored as flexible `VARCHAR(3)` without hardcoding USD.

4. **Outreach Dispatch Provider (D-04):** Transactional email provider selection (e.g., Resend vs. Postmark).
5. **Audit Log Retention Period (D-05):** Cold storage archiving vs. rolling 12-month partition.

## 10. Known Limitations

1. **Static Validation Posture:** Validation was performed via static AST parsers (`sqlparse` and Python scripts). In accordance with design-only rules, no runtime database migrations were executed.
2. **Statutory Public Holiday Handling:** The `add_business_days` function skips Saturdays and Sundays in the partner's operating timezone, but does not hardcode jurisdiction-specific statutory public holidays. Custom holiday calendars can be added in Phase 3.
3. **Pre-Operational Delivery Freeze:** Projects cannot enter active implementation until the founder authorizes delivery readiness and the technical team is onboarded.
